# Mini Log Management System

[![CI/CD](https://github.com/SAISENGMAIN6631503085/log-mgmt/actions/workflows/ci.yml/badge.svg)](https://github.com/SAISENGMAIN6631503085/log-mgmt/actions/workflows/ci.yml)

**Live demo (SaaS mode): https://14.207.143.101.sslip.io**. Login details are sent separately;
the passwords and API keys there are not the demo values in this repo.
On the live demo, **syslog (port 514) is closed on purpose**: syslog has no authentication, so it's
not exposed to the internet. Try syslog in appliance mode (Quick start below), or send firewall
logs to the live demo over HTTPS with an API key (`POST /ingest`). Everything else works on both.

A multi-tenant log management / SIEM-lite system:
- It ingests logs from firewalls, network devices, applications, AWS CloudTrail, Microsoft 365,
  Active Directory and CrowdStrike, and normalizes them into one schema (a Go service).
- It stores them in ClickHouse (one partition per day) and offers search, a dashboard and alerts; PostgreSQL keeps users, API keys and alerts.
- Each tenant only ever sees its own data.

It runs the same way on one VM (**appliance**) or on a public cloud VM with a real HTTPS domain (**SaaS**).

## Quick start (appliance mode, ~2 minutes)
Requires Docker with Compose, make and python3.
```
make up      # build and start everything; creates .env from .env.example on first run
make seed    # users admin / viewerA / viewerB + demo API keys
make demo    # load all sample logs (syslog, JSON API, file upload)
```
Open **https://localhost** and sign in as `admin` (password: `SEED_ADMIN_PASSWORD` in `.env`).
The browser shows "Not secure" in appliance mode: each install makes its own certificate, which
your computer doesn't know yet. Traffic is still encrypted. Click through, or trust that install's
certificate on your computer once (one command; this is what the demo video's Mac did), see
[setup_appliance.md](docs/setup_appliance.md#5-the-browser-certificate-warning).

Change the secrets in `.env` before running this anywhere real.

## Checking the assignment requirements
Run `make up && make seed`, then work through the assignment's acceptance checklist:

| Assignment checklist item | How to check it |
|---|---|
| Start in appliance mode | `make up`. It prints `{"status":"ok","database":"ok"}` |
| Syslog appears in the UI within a minute | `./samples/send_syslog.sh`, or the PDF lines with `nc -u -w1 127.0.0.1 514`, then **Search** |
| `POST /ingest` with the sample JSON, then search | Postman folder **Assignment samples (section 4)**, or `curl -k https://localhost/ingest -H "X-API-Key: lm_demoA_dev_key_change_me" -H "content-type: application/json" -d '<sample>'` |
| AWS / M365 / AD files are normalized | **Add logs** page: drop `samples/aws_cloudtrail.json` (or the M365 / AD sample), then **See them**. Or `make demo` |
| Top N, timeline, tenant/source/time filters | **Overview**: Source filter + 1h/24h/7d, the timeline, top IPs / users / events; tenant switcher top right (admin) |
| Alert rule fires | `make simulate` (an attack every 2 min: brute force, port scan, malware in turn) or `make demo`, then **Alerts**; tune rules on the **Rules** page; webhook via `ALERT_WEBHOOK_URL` |
| Viewer sees only their tenant | Sign in as `viewerA`; asking for `?tenant=demoB` returns 403 (Postman folder **Tenant isolation**) |
| SaaS over HTTPS | The live demo above (real Let's Encrypt certificate); install steps in [docs/setup_saas.md](docs/setup_saas.md) |

Notes on the samples:
- The PDF samples are dated 2025, older than the 7-day retention. They are stored at the time they
  arrive and tagged **time_adjusted**; the original time is kept in the raw log. Search the last 24 h to find them.
- Each sample must be sent with **its own tenant's key** (demoA samples with the demoA key). A sample
  sent with another tenant's key is rejected.

## Make targets
| Target | What it does |
|--------|--------------|
| `make up` | build + start all services, wait until healthy, check `/health` |
| `make down` | stop everything (data volumes are kept) |
| `make seed` | create demo users and API keys (safe to re-run) |
| `make test` | run pytest from `/tests` inside the backend image, then the Go tests of the ingest service |
| `make logs` | follow logs from all services |
| `make demo` | send every sample through syslog, the JSON API and file upload |
| `make simulate` | live random traffic, with an attack every 2 minutes (brute force, port scan, malware in turn) |
| `make retention` | drop days of events older than `RETENTION_DAYS` now (also runs hourly) |

## Services
| Service | Role | Exposed on the host |
|---------|------|---------------------|
| caddy | TLS + reverse proxy: `/ingest`, `/api/ingest/*` → ingest; other `/api/*`, `/health`, `/docs` → backend; everything else → frontend | 80, 443 |
| ingest | **Go**: receives every log (JSON, files, syslog from Vector), normalizes it, adds the country, skips duplicates, stores it in ClickHouse | – |
| backend | **Python** FastAPI: login, search, dashboard, alerts, API keys, rules; alert worker + retention jobs | – |
| frontend | React SPA (dashboard, search, alerts), served as static files | – |
| postgres | PostgreSQL 16: users, API keys, alerts, settings | – |
| clickhouse | ClickHouse 24.8: column store for the events, memory-capped for small VMs (see below) | – |
| vector | syslog receiver → ingest | 514/udp, 514/tcp (`SYSLOG_BIND`) |
| simulator | optional live demo traffic (`COMPOSE_PROFILES=demo` in `.env`; on in the live demo) | – |

All images run on linux/amd64 and linux/arm64.

## Extras beyond the assignment
- **Country enrichment (GeoIP):** each event's source IP gets a country at ingest (DB-IP Lite, CC BY 4.0),
  shown as flags in Search and Alerts, a "Top countries" table and a country filter. Only public
  internet addresses have a country: internal ones (10.x, 192.168.x, 172.16–31.x) and the example
  ranges in the assignment samples (203.0.113.x, 198.51.100.x) correctly show no flag.
- **Three detection rules** (brute force, firewall scan, malware), tunable per tenant on the **Rules** page.
- **Add logs** page (file upload in the browser) and an **API keys** page (create, show once, revoke).
- **Live demo traffic:** with `COMPOSE_PROFILES=demo`, a simulator (`samples/simulator.py`, its own
  container) keeps the demo fresh. Its addresses are real public ranges, so countries show up, but
  every log is generated, and the website shows a **Demo data** label. It does two things:
  - a **steady stream** of ordinary logs, a few every second, about 30,000 a day for demoA (which
    also receives all the syslog) and 15,000 for demoB; none of it reaches an alert threshold;
  - a **staged attack every 15 minutes** (brute force, port scan, malware in turn), so about four
    alerts an hour. The logs are fake, but the alerts are real detections by the normal rules.

  With 7-day retention that's at most about 340,000 logs, roughly 40–50 MB in ClickHouse.
- **CI/CD** with GitHub Actions, and a hardened SaaS server.

## Tests
`make test` runs two suites. **pytest** (`/tests`) covers login and **tenant isolation**, search, the
alert rules and webhook, retention and stats, and sends logs end to end through the running ingest
service (duplicates, the assignment's samples, API keys). **go test** (`/ingest`) covers every
normalizer, file parsing, the ingest endpoints and the ClickHouse writer. Database tests use the
compose services and are skipped if they aren't running, so run `make up && make seed` first.

GitHub Actions ([.github/workflows/ci.yml](.github/workflows/ci.yml)) does exactly that on every push:
`make up`, `make seed`, `make test` (failing if any test was skipped), and a TypeScript build of the
frontend. When `main` is green it redeploys the live demo; see
[setup_saas.md](docs/setup_saas.md#7-continuous-deployment).
